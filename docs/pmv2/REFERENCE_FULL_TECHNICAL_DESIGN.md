# وحدة المهام اليومية والصيانة الدورية الجديدة — الخطة النهائية والتصميم الفني

## 0. قرار معماري ملزم

يتم بناء وحدة جديدة مستقلة بالكامل باسم عمل مؤقت **PM V2 — المهام اليومية والصيانة الدورية**.

- لا يتم تعديل جداول الصيانة الدورية القديمة أثناء البناء.
- لا يتم تعديل أي Workflow قائم في البلاغات أو المخزون أو المستودعات أو المشتريات أو المسار B.
- الوحدة الجديدة تستخدم البيانات والخدمات الحالية فقط عند الحاجة: المستخدمون/الفنيون، المخازن الفرعية، الأصناف والمخزون، وWorkflow الشراء Path B.
- كل جداول الوحدة الجديدة تحمل بادئة `pmv2_` لضمان العزل الكامل أثناء فترة التعايش.
- بعد اكتمال الوحدة الجديدة واختبارها واعتمادها، يتم تعطيل الوحدة القديمة أولاً، ثم إجراء فحص اعتماديات، ثم حذفها بعملية تنظيف مستقلة ومخططة دون حذف أو تعديل أي مكون مشترك مع النظام.
- عند حذف القديم لاحقاً لا يتم حذف ملفات migrations التاريخية؛ يتم إنشاء migration جديد لإسقاط الجداول القديمة بعد إثبات عدم استخدامها.

# الجزء الأول — الخطة التشغيلية النهائية

## 1. الهدف

تكون تجربة الفني على الآيباد أو الهاتف في أبسط صورة ممكنة:

**مهامي اليوم → افتح الموقع → بند واحد → اختر النتيجة → التالي → إنهاء الزيارة**

الكتابة ليست جزءاً أساسياً من عمل الفني. الأصل هو النقر والاختيار والتصوير، والكتابة تظهر فقط عند الضرورة.

## 2. إعداد الإدارة

### 2.1 المواقع

تنشئ الإدارة مجموعات مواقع مثل:

- المطاعم
- الألعاب الهيدروليكية
- المكاتب الرئيسية
- مرافق الحديقة
- أي مجموعة أخرى

وتحت كل مجموعة المواقع الفعلية، مثل المطاعم 1–20 والألعاب 1–18.

المواقع في PM V2 مستقلة عن شجرة الصيانة القديمة. يمكن الاحتفاظ بربط اختياري بموقع أو أصل حالي في النظام إذا احتجنا للتقارير مستقبلاً، دون أن يصبح هذا الربط شرطاً لتشغيل الوحدة.

### 2.2 فرق الصيانة

تنشئ الإدارة فرقاً مثل:

- الكهرباء
- السباكة
- الإنشاءات
- الميكانيكا
- الهيدروليك

لا يتم إنشاء فنيين جدد. أعضاء الفريق يتم اختيارهم من الفنيين/المستخدمين الحاليين في النظام.

### 2.3 مخزن الفريق

لا يتم إنشاء مخزون جديد داخل PM V2.

عند إعداد الفريق تظهر قائمة منسدلة بالمخازن الفرعية الفعالة الموجودة حالياً في نظام المستودعات، ويتم ربط الفريق بأحدها.

مثال:

**فريق الكهرباء → مخزن الكهرباء الفرعي**

عندما يستخدم الفني خيار **مخزوني** تظهر له أصناف هذا المخزن الفرعي فقط.

### 2.4 حساب الآيباد/الفريق

يتم ربط الفريق بحساب مستخدم حالي مخصص لآيباد/هاتف الفريق، أو بحساب الفريق المعتمد للتشغيل. عند تسجيل الدخول يعرف النظام الفريق تلقائياً ولا يطلب من الفني اختيار القسم في كل مرة.

## 3. قوائم الفحص

يتم إنشاء Checklist كقالب reusable حسب الفريق ونوع الموقع، مثل:

- كهرباء المطاعم
- سباكة المطاعم
- هيدروليك الألعاب

القالب ينشأ مرة واحدة ثم يربط بعدة مواقع.

## 4. جدولة كل بند بشكل مستقل

لكل بند داخل Checklist تكراره الخاص، وليس للقائمة كلها تكرار واحد.

أمثلة:

- فحص الإنارة: يومي
- فحص السوكتات: أسبوعي — يوم الأحد
- فحص لوحة الكهرباء: شهري — يوم 1
- فحص التوصيلات الرئيسية: كل 3 أشهر — وفق تاريخ بداية البرنامج

النظام يحسب الاستحقاق تلقائياً.

## 5. برنامج الصيانة

برنامج الصيانة هو الربط بين:

**المواقع + فريق الصيانة + Checklist + تاريخ البداية**

مثال:

**جميع المطاعم + فريق الكهرباء + Checklist كهرباء المطاعم + بداية 1 أكتوبر**

## 6. توليد مهام اليوم

كل يوم يحسب النظام البنود المستحقة.

إذا كان لنفس الفريق في نفس الموقع عدة بنود مستحقة في نفس اليوم، يتم جمعها في **مهمة واحدة للموقع**.

مثال:

مطعم 1 اليوم مستحق فيه:

- الإنارة اليومية
- السوكتات الأسبوعية
- اللوحة الشهرية

يظهر للفني:

**مطعم 1 — 3 بنود**

ولا تظهر ثلاث مهام منفصلة.

## 7. شاشة الفني

تحتوي الصفحة الرئيسية للفني على قسمين فقط:

### مهامي اليوم

الأعمال التي يستطيع تنفيذها الآن.

### طلبات معلقة

الأعمال التي تنتظر المستودع أو الشراء أو الصرف، وبالتالي لا يستطيع الفني تنفيذها الآن.

## 8. تنفيذ Checklist بنداً بنداً

عند فتح المهمة تظهر شاشة واحدة لكل بند.

مثال:

**البند 1 من 5 — فحص السوكتات**

الأزرار الكبيرة:

- ✅ سليم
- 🔧 تم الإصلاح
- ⚠️ يحتاج صيانة

بعد إكمال الإجراء ينتقل النظام تلقائياً للبند التالي.

يوجد زر رجوع صغير لتصحيح اختيار سابق عند الحاجة، مع شريط تقدم مثل **2 / 5**.

## 9. سليم

يضغط الفني **سليم** وينتقل مباشرة للبند التالي.

لا ملاحظة إلزامية ولا كتابة.

## 10. تم الإصلاح

تعني أن المشكلة تم حلها بالفعل.

يظهر سؤال واحد:

**هل استخدمت قطعة؟ — لا / نعم**

- لا: الانتقال للبند التالي.
- نعم: تظهر قائمة أصناف مخزن الفريق، يختار الصنف والكمية بأزرار + و- ثم يؤكد.

لا توجد كتابة إلزامية.

## 11. يحتاج صيانة

تعني أن المشكلة لم تحل بعد.

يظهر خياران فقط:

- 📦 سحب من مخزوني
- 🛒 طلب مواد

### سحب من مخزوني

يختار الفني الصنف والكمية من مخزن فريقه الفرعي، ويتم تسجيل الاستخدام عبر خدمات المخزون الحالية. بعد الإصلاح تتحول نتيجة البند إلى **تم الإصلاح**.

### طلب مواد

يعرض النظام أصناف النظام للبحث والاختيار، ثم يحدد الفني الكمية ويرسل للمستودع.

إذا لم يجد الصنف، يوجد خيار ثانوي فقط:

**صنف غير موجود بالقائمة**

وهنا فقط تصبح الكتابة ضرورية.

## 12. الصور والملاحظات

- الصورة اختيارية ومتاحة بزر واضح 📷.
- الملاحظة اختيارية عبر زر **+ ملاحظة** ولا تظهر كحقل كتابة دائم.
- الأصل هو الصورة والاختيارات، وليس النص.

## 13. طلب المستودع

عند طلب المواد يصبح البند في حالة معلقة، ويظهر للفني داخل **طلبات معلقة**.

المستودع يرى:

- المهمة
- الموقع
- الفريق
- الصنف
- الكمية
- بند الفحص المرتبط

وله مساران:

### المادة متوفرة

يتم صرفها/تحويلها للفريق باستخدام **نفس خدمات وآلية المخزون والمستودعات الحالية** دون أي خصم مباشر من PM V2. تبقى جميع متطلبات الحركة الحالية سارية، بما فيها QR/Lot Tracking والتحقق من الكمية عندما تكون مطلوبة.

### المادة غير متوفرة

يظهر زر:

**إنشاء طلب شراء خارجي**

## 14. الشراء الخارجي — Path B

لا يتم إنشاء Workflow شراء جديد ولا تعديل Path B.

لأن Path B الحالي مرتبط تقنياً ببلاغ صيانة، يستخدم PM V2 **بلاغ جسر داخلي** للشراء الخارجي:

1. يبدأ المستودع طلب الشراء الخارجي من شاشة PM V2.
2. تنشئ PM V2/Adapter بلاغ الجسر المطلوب وتربطه بالمهمة الأصلية وبندها وطلب المادة.
3. يكمل المستخدم المخول أصلًا داخل Path B إنشاء/إدارة Purchase Order حسب الصلاحيات الحالية؛ لا تضيف PM V2 صلاحية إنشاء PO لدور المستودع.
4. تحفظ PM V2 داخل جداولها مراجع بلاغ الجسر وPurchase Order مع بقاء الربط بالمهمة الأصلية.
5. لا يحتاج الفني إلى فتح البلاغ الجسر أو التعامل معه.
6. PM V2 تقرأ حالة المسار B وتعرضها للفني بصياغة مبسطة فقط.

سلسلة الربط المطلوبة هي:

`PM V2 Task → Task Item → Material Request → Bridge Ticket/Item → Purchase Order`

وبذلك لا نغير أي Workflow أو قواعد اعتماد أو صلاحيات في Path B.

## 15. الطلبات المعلقة

يعرض الفني بطاقات بسيطة مثل:

**مطعم 3 — سوكت 13A × 2**

الحالة قد تكون:

- بانتظار المستودع
- قيد الشراء الخارجي
- تم الشراء وبانتظار الاستلام
- تم الاستلام وبانتظار الصرف

ويظهر زر واحد:

**🔔 تذكير**

النظام يرسل التذكير بدون أن يكتب الفني رسالة.

## 16. وصول المادة والعودة لمهامي

مجرد وصول المادة إلى المستودع لا يعيد المهمة للفني.

المسار الصحيح:

**وصول → استلام المستودع → صرف/تسليم للفريق → جاهزة للإصلاح**

عند الصرف للفريق تخرج من **طلبات معلقة** وتظهر في **مهامي اليوم** بعلامة:

**🔧 متابعة إصلاح**

إذا لم تنفذ اليوم، تبقى نفس المهمة وتظهر في اليوم التالي. لا تنشأ نسخة جديدة كل يوم.

## 17. إنهاء الزيارة

بعد آخر بند تظهر شاشة ملخص قصيرة، ثم:

- رئيس المهمة: اختيار اسم واحد من فنيي الفريق.
- المشاركون: اختيار متعدد من فنيي الفريق.
- + إضافة فني من فريق آخر: اختيار اختياري من الفنيين الحاليين.

ثم:

**اعتماد وإنهاء الزيارة**

كل هذا اختيار بالنقر دون كتابة.

## 18. إنهاء الزيارة مقابل الإغلاق النهائي

إنهاء الزيارة يسجل أن الفريق أنهى زيارة اليوم.

إذا بقي بند ينتظر مادة، تبقى المهمة مفتوحة.

بعد وصول المادة قد تتم زيارة متابعة بفنيين مختلفين، ولذلك يتم تسجيل رئيس وأعضاء كل زيارة بشكل مستقل.

عندما تنتهي جميع البنود ولا يبقى أي طلب معلق، يتم إغلاق المهمة نهائياً.

# الجزء الثاني — التصميم الفني

## 19. حدود الوحدة

### داخل نطاق PM V2

- إعداد المواقع.
- إعداد فرق الصيانة وروابط الفنيين والمخازن الفرعية والحسابات.
- قوالب Checklist وجدولة كل بند.
- برامج الصيانة وربطها بالمواقع.
- توليد مهام اليوم.
- تنفيذ الفني.
- الزيارات وأعضاء التنفيذ.
- الطلبات المعلقة.
- طبقة الربط مع المخزون والمستودع وPath B.
- التنبيهات الخاصة بالوحدة.

### خارج النطاق وغير قابل للتعديل

- Workflow البلاغات الحالي.
- Workflow Path B.
- جداول المستخدمين الأساسية.
- جداول المخازن والمخزون الأساسية.
- Workflow الاستلام والصرف الحالي.
- Workflow المشتريات والموافقات الحالي.
- بقية التقارير والوحدات الحالية.

أي تعديل خارج الوحدة أثناء التركيب يكون **تسجيلاً additive فقط** مثل إضافة route أو router جديد، دون تغيير سلوك الموجود.

# 20. تصميم قاعدة البيانات الجديدة

جميع الجداول التالية جديدة وتحمل بادئة `pmv2_`.

## 20.1 pmv2_location_groups

مجموعات المواقع.

الحقول الرئيسية:

- `id`
- `name`
- `code`
- `sortOrder`
- `isActive`
- `createdById`
- `createdAt`
- `updatedAt`

## 20.2 pmv2_locations

المواقع الفعلية.

- `id`
- `groupId`
- `name`
- `code`
- `sortOrder`
- `isActive`
- `existingSiteId` nullable — ربط اختياري بموقع حالي
- `existingAssetId` nullable — ربط اختياري بأصل حالي
- `createdById`
- timestamps

## 20.3 pmv2_teams

فرق الصيانة.

- `id`
- `name`
- `code`
- `warehouseId` — يشير إلى `warehouses.id` الحالي، ويجب أن يكون مخزناً فرعياً فعالاً
- `tabletUserId` nullable — حساب المستخدم الحالي الخاص بآيباد/هاتف الفريق
- `isActive`
- timestamps

لا نكرر بيانات المخزن أو المستخدم.

## 20.4 pmv2_team_members

أعضاء الفريق من المستخدمين الحاليين.

- `id`
- `teamId`
- `userId` → `users.id`
- `isActive`
- timestamps

قيد فريد مقترح: `(teamId, userId)`.

## 20.5 pmv2_checklists

قوالب قوائم الفحص.

- `id`
- `teamId`
- `name`
- `description` nullable
- `isActive`
- `createdById`
- timestamps

## 20.6 pmv2_checklist_items

بنود القالب وجدولتها.

- `id`
- `checklistId`
- `title`
- `sortOrder`
- `isRequired`
- `frequency` enum: `daily | weekly | monthly | quarterly | biannual | annual`
- `frequencyValue` default 1
- `weekday` nullable — للأسبوعي
- `monthDay` nullable — للشهري والدورات الشهرية
- `anchorDate` nullable — مرجع بداية الدورة
- `isActive`
- timestamps

## 20.7 pmv2_programs

برنامج صيانة يربط الفريق والقائمة بتاريخ بداية.

- `id`
- `name`
- `teamId`
- `checklistId`
- `startDate`
- `isActive`
- `createdById`
- timestamps

## 20.8 pmv2_program_locations

ربط البرنامج بعدة مواقع.

- `id`
- `programId`
- `locationId`
- `isActive`
- timestamps

قيد فريد: `(programId, locationId)`.

## 20.9 pmv2_tasks

تمثل أمر/مهمة الصيانة المستمرة للموقع والفريق لذلك الاستحقاق.

- `id`
- `taskNumber`
- `programId`
- `locationId`
- `teamId`
- `dueDate`
- `status`: `open | in_progress | pending_followup | ready_followup | completed | cancelled`
- `firstStartedAt` nullable
- `completedAt` nullable
- `createdAt`
- `updatedAt`

قاعدة أساسية: نفس الفريق + نفس الموقع + نفس تاريخ الاستحقاق يجمع البنود في مهمة واحدة.

## 20.10 pmv2_task_items

Snapshot للبنود المستحقة فعلياً عند إنشاء المهمة.

- `id`
- `taskId`
- `sourceChecklistItemId`
- `titleSnapshot`
- `scheduledDate`
- `sortOrder`
- `status`: `pending | ok | fixed | waiting_material | ready_followup | resolved`
- `resolvedAt` nullable
- timestamps

الـSnapshot يمنع تعديل القالب لاحقاً من تغيير سجل مهمة قديمة.

قيد فريد مقترح لمنع التكرار:

`(taskId, sourceChecklistItemId, scheduledDate)`.

## 20.11 pmv2_visits

كل دخول فعلي للموقع، سواء فحص أول أو متابعة إصلاح.

- `id`
- `taskId`
- `visitType`: `inspection | followup_repair`
- `teamId`
- `startedById`
- `startedAt`
- `endedAt` nullable
- `status`: `in_progress | completed`
- `leaderUserId` nullable حتى الإنهاء
- `summaryNote` nullable — استثنائي وليس إلزامياً
- timestamps

## 20.12 pmv2_visit_members

الأشخاص الذين شاركوا في الزيارة.

- `id`
- `visitId`
- `userId`
- `memberTeamId` nullable — الفريق الذي ينتمي له وقت التنفيذ
- `role`: `leader | member | external_member`
- timestamps

## 20.13 pmv2_item_actions

سجل زمني لكل إجراء تم على بند الفحص.

- `id`
- `taskItemId`
- `visitId`
- `action`: `ok | fixed | needs_maintenance | material_used | material_requested | photo_added | note_added | resolved`
- `performedById`
- `note` nullable
- `photoUrl` nullable
- `createdAt`

هذا الجدول هو سجل التدقيق ولا يعتمد على النصوص الإلزامية.

## 20.14 pmv2_material_requests

رأس طلب المواد المرتبط ببند ومهمة.

- `id`
- `taskId`
- `taskItemId`
- `requestedById`
- `teamId`
- `teamWarehouseId`
- `status`: `waiting_warehouse | external_purchase | received_warehouse | issued_to_team | cancelled`
- `linkedBridgeTicketId` nullable
- `linkedPurchaseOrderId` nullable
- `createdAt`
- `updatedAt`

## 20.15 pmv2_material_request_items

بنود طلب المواد.

- `id`
- `requestId`
- `catalogItemId` nullable
- `inventoryId` nullable
- `itemNameSnapshot`
- `requestedQuantity`
- `unitSnapshot` nullable
- `status`
- timestamps

يسمح `itemNameSnapshot` بتسجيل حالة الصنف غير الموجود بالقائمة دون تعديل Catalog الحالي.

## 20.16 pmv2_material_usages

توثيق المواد التي استخدمت فعلياً في الإصلاح.

- `id`
- `taskId`
- `taskItemId`
- `visitId`
- `warehouseId`
- `inventoryId`
- `quantity`
- `inventoryTransactionId` nullable — مرجع للحركة التي أنشأتها خدمة المخزون الحالية
- `usedById`
- `createdAt`

هذا الجدول لا يغير رصيد المخزون بنفسه؛ الرصيد يتحرك عبر الخدمة الحالية ثم تحفظ PM V2 المرجع.

## 20.17 pmv2_request_reminders

تسجيل ضغط زر التذكير.

- `id`
- `materialRequestId`
- `sentById`
- `sentAt`

يمنع الاعتماد على نصوص يكتبها الفني ويعطي الإدارة سجل متابعة واضحاً.

# 22. قواعد الجدولة

1. Scheduler خاص بـ PM V2 فقط.
2. يعمل بشكل idempotent؛ تشغيله أكثر من مرة لا ينشئ مهام مكررة.
3. يحسب تاريخ الرياض عند تحديد مهام اليوم.
4. لكل Program + Location يحسب البنود المستحقة.
5. يجمعها في Task واحدة للفريق والموقع والتاريخ.
6. ينشئ Task Items كنسخة ثابتة Snapshot.
7. المهمة غير المنفذة لا يعاد إنشاؤها في اليوم التالي؛ تبقى نفس المهمة مفتوحة.
8. مهمة المتابعة الجاهزة للإصلاح تظهر ضمن مهام اليوم إلى أن تغلق.

# 24. صلاحيات الوحدة

لا تنشأ Roles جديدة في النظام الحالي في المرحلة الأولى.

يتم استخدام الأدوار الحالية:

- Admin / Maintenance Manager: إعداد ومتابعة PM V2.
- Technician / حساب الفريق: مهام الفريق فقط.
- Warehouse: طلبات مواد PM V2 فقط إضافة إلى صلاحياته الحالية.
- Purchase roles: تستمر في Path B الحالي بدون أي تغيير.

إضافة إلى الدور، PM V2 تتحقق من عضوية الفريق حتى لا يرى الفني مهام فريق آخر.

# 26. طبقات التكامل مع النظام الحالي

يمنع استدعاء جداول النظام الحالي مباشرة من واجهات PM V2 بطرق متفرقة. يتم وضع Adapters واضحة:

- `CurrentUsersAdapter` — قراءة الفنيين والمستخدمين الحاليين.
- `WarehouseAdapter` — قراءة المخازن الفرعية وتنفيذ نفس حركة الصرف/التحويل عبر الخدمة الحالية، مع الحفاظ على QR/Lot Tracking والتحققات القائمة.
- `InventoryAdapter` — قراءة الأصناف والكميات من المخزن المرتبط بالفريق وتسجيل الاستخدام عبر مرجع حركة النظام الحالي دون خصم مباشر.
- `PathBAdapter` — إنشاء/ربط بلاغ الجسر، حفظ سلسلة الربط بالمهمة الأصلية، وقراءة حالة Path B؛ أما إنشاء/إدارة Purchase Order فيتم وفق صلاحيات Path B الحالية بواسطة المستخدم المخول أصلًا.

هذا يقلل خطر التأثير على النظام ويجعل إزالة الوحدة القديمة لاحقاً مستقلة.

# 27. حالات العمل المبسطة

```text

                         ↓
                    ISSUE_TO_TEAM

                    READY_FOLLOWUP
```

# 28. قواعد UX للفني — ملزمة

1. شاشة واحدة = قرار واحد قدر الإمكان.
2. الأزرار كبيرة ومناسبة للمس باليد.
3. لا يوجد إدخال نص إلزامي للحالات الطبيعية.
4. القوائم تعرض الاختيارات ذات الصلة فقط.
5. أسماء الفنيين اختيار وليس كتابة.
6. الأصناف اختيار من المخزون/الكتالوج وليس كتابة، إلا للصنف غير الموجود.
7. الكمية بأزرار `+ / -` مع إمكانية لوحة أرقام عند الكميات الكبيرة.
8. الصور أسهل من الوصف النصي وتكون متاحة بضغطة واحدة.
9. بعد إنهاء بند ينتقل تلقائياً للتالي.
10. لا تظهر للفني مصطلحات تقنية مثل Main Plan أو Sub Plan أو Work Order أو Path B.
11. لا تظهر مهمة غير قابلة للتنفيذ داخل مهامي اليوم؛ الطلب المنتظر مكانه طلبات معلقة.
12. لا يضيع أي طلب معلق حتى لو لم يتصرف المستودع؛ يبقى ظاهراً مع زر تذكير.

# 29. الاختبارات المطلوبة قبل الاعتماد

## الجدولة

- يومي.
- أسبوعي في يوم محدد.
- شهري في يوم محدد.
- كل 3 أشهر.
- عدم تكرار المهمة عند تشغيل Scheduler أكثر من مرة.
- جمع عدة بنود مستحقة لنفس الموقع والفريق في مهمة واحدة.

## الفني

- سليم.
- إصلاح بدون قطعة.
- إصلاح بقطعة من مخزن الفريق.
- يحتاج صيانة ثم طلب مواد.
- إنهاء زيارة مع طلب معلق.
- اختيار رئيس وأعضاء من الفريق.
- إضافة فني من فريق آخر.

## المستودع

- صرف مادة متوفرة للفريق.
- عدم توفر المادة وتحويلها للشراء الخارجي.
- بقاء الطلب معلقاً إذا لم يعالجه المستودع.
- زر التذكير.

## Path B

- إنشاء بلاغ الجسر.
- إنشاء طلب شراء عبر المسار B الحالي.
- عدم تغيير أي حالة أو Rule في المسار الحالي.
- استلام المشتريات.
- عدم عودة المهمة للفني قبل صرف المادة للفريق.
- العودة إلى مهامي اليوم بعد الصرف.

## المتابعة

- مهمة متابعة لم تنفذ اليوم تظهر غداً بنفس ID.
- زيارة إصلاح جديدة يمكن أن يكون لها رئيس وأعضاء مختلفون.
- الإغلاق النهائي لا يحدث مع وجود بند أو طلب معلق.

## Regression

إجراء Regression كامل على:

- البلاغات الحالية.
- Path B الحالي.
- المخزون والتحويلات.
- الاستلام.
- طلبات الشراء.

والشرط: لا يتغير سلوكها بسبب PM V2.

# 30. خطة الإطلاق وحذف الوحدة القديمة

## المرحلة A — البناء

- إنشاء جداول PM V2 فقط.
- إنشاء Backend وFrontend مستقلين.
- عدم لمس بيانات PM القديم.

## المرحلة B — Pilot

تشغيل محدود على مثال حقيقي، مثل:

**فريق الكهرباء + عدد صغير من المطاعم**

واختبار الدورة كاملة من الجدولة إلى الإغلاق والشراء الخارجي.

## المرحلة C — التشغيل الكامل

- إضافة بقية المطاعم.
- الألعاب.
- المكاتب والمرافق.

## المرحلة D — إيقاف القديم

- إزالة رابط الوحدة القديمة من الواجهة أو تحويلها إلى غير متاحة.
- عدم حذف الجداول بعد.
- مراقبة النظام والتأكد من عدم وجود اعتماد عليها.

## المرحلة E — تنظيف القديم

بعد اعتماد صاحب المشروع:

1. Dependency audit على كل `preventive_plans`, `pm_main_plans`, `pm_sub_plans`, `pm_work_orders` والجداول القديمة المرتبطة.
2. حذف Routes/Components/Jobs القديمة التي ثبت أنها خاصة بالوحدة القديمة فقط.
3. Migration جديد لإسقاط الجداول القديمة غير المشتركة.
4. إزالة exports والـschema القديم من الكود.
5. Regression نهائي على النظام القائم.

لا يتم حذف أي جدول أو Function مشترك مع بقية النظام.

# 31. معيار نجاح الوحدة

تعتبر الوحدة ناجحة عندما يستطيع الفني تنفيذ يوم كامل من العمل على الآيباد عبر:

**نقر واختيار وتصوير فقط تقريباً**

دون الحاجة لفهم الجدولة أو المخزون أو المشتريات أو المسار B، بينما تستطيع الإدارة تتبع:

- ماذا كان مستحقاً؟
- ماذا تم فحصه؟
- ماذا تم إصلاحه؟
- ما المادة المستخدمة؟
- ماذا ينتظر المستودع أو الشراء؟
- من كان رئيس المهمة ومن شارك؟
- متى أغلق العطل فعلياً؟

وهذا مع بقاء جميع Workflows الحالية في النظام دون تعديل.
