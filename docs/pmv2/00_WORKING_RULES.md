# قواعد العمل الملزمة — PM V2

## 1. حماية النظام الحالي

النظام الحالي يعمل لدى العميل، لذلك:

- ممنوع تغيير أي Workflow قائم خارج PM V2 لكي يتوافق معها.
- ممنوع تعديل سلوك البلاغات الحالية دون قرار مستقل وصريح.
- ممنوع تعديل Workflow المشتريات أو Path B.
- ممنوع تعديل منطق المخزون أو المستودعات القائمة.
- ممنوع إنشاء Users أو Warehouses أو Catalog أو Inventory بديل داخل PM V2.
- ممنوع حذف الوحدة القديمة أثناء البناء.

**PM V2 هي التي تتكيف مع النظام الحالي، وليس العكس.**

## 2. النموذج المعماري المعتمد

PM V2 هي:

**وحدة مستقلة معماريًا داخل نفس البرنامج**.

هذا يعني:

- ليست تطبيقًا منفصلًا أو Microservice في المرحلة الحالية.
- ليست كودًا متداخلًا عشوائيًا داخل الوحدات القائمة.
- لها Namespace وحدود واضحة للـFrontend والـBackend والـDomain والـDatabase.
- تستخدم الخدمات والـMaster Data الحالية عبر Adapters محددة.

## 3. قاعدة عدم تكرار الموجود

قبل إنشاء أي جدول أو شاشة أو Service جديدة يجب طرح السؤال:

> هل هذه القدرة أو البيانات موجودة أصلًا في البرنامج ويمكن إعادة استخدامها؟

إذا كانت موجودة وتصلح كمصدر حقيقة مشترك:

- يتم الربط بها.
- لا تنشأ نسخة PM V2 منها.
- لا تنسخ بياناتها إلى Master Data موازية إلا إذا كان هناك سبب تشغيلي موثق ومعتمد.

أمثلة مرجعية حالية:

- المواقع: `sites`
- أقسام الموقع: `sections`
- الأصول: `assets`
- المستخدمون: `users`
- المخازن: `warehouses`
- الكتالوج: `catalog_items`
- المخزون والحركات والـLots: النظام الحالي
- الشراء: Path B / Purchase Orders الحالية

## 4. Integration Boundary

لا يسمح لأي Service عادية داخل PM V2 بالاعتماد المباشر وغير المنظم على وحدات النظام الحالي.

التكامل يتم عبر Adapters/Services واضحة مثل:

- Users Adapter
- Organization/Department Adapter عند الحاجة
- Maintenance Target Adapter (`sites / sections / assets`)
- Warehouse Adapter
- Inventory Adapter
- Path B Adapter
- Notifications Adapter
- File/Image Adapter

## 5. ما تملكه PM V2

PM V2 تملك فقط منطقها التشغيلي الجديد، مثل:

- التخصصات.
- الفرق.
- أعضاء الفرق كعلاقات مع Users الحاليين.
- مسؤول التخصص.
- Checklists.
- Recurrence.
- Maintenance Programs.
- Tasks / Task Items.
- Visits / Visit Members.
- Material Request state من منظور الصيانة.
- Follow-up / Closure.
- Audit التشغيلي الخاص بالوحدة.

## 6. الهيكل التنظيمي

المسمى المعتمد:

**القسم الحالي → التخصص → الفريق → الأعضاء**

قواعده:

- القسم الحالي لا يعاد إنشاؤه في PM V2.
- التخصص كيان PM V2 تنظيمي.
- الفريق تابع لتخصص.
- أعضاء الفريق Users حاليون.
- مسؤول التخصص منفصل عن رئيس المهمة.
- رئيس المهمة يحدد لكل زيارة.
- `sections` تعني قسمًا مكانيًا داخل Site وليست التخصص أو القسم الوظيفي.

## 7. أسلوب البناء

- الجداول الجديدة الخاصة بالوحدة تحمل بادئة `pmv2_`.
- Routes/Services الجديدة توضع في Namespace PM V2 واضح.
- Jobs/Scheduler تكون خاصة بالوحدة.
- الكود المشترك الموجود يعاد استخدامه عند ملاءمته بدل نسخه.
- أي تسجيل خارج PM V2 يكون Additive ومحدودًا مثل Route/Menu registration، ولا يغير السلوك القائم.

## 8. Acceptance Gate إلزامي لكل مرحلة

لا تعتبر أي مرحلة مكتملة بمجرد انتهاء الكود.

المسار الإلزامي:

**Implementation → Test → Fix → Re-test → Acceptance Gate → Next Phase**

لا تبدأ المرحلة التالية إذا لم ينجح Gate المرحلة الحالية.

## 9. قاعدة "أجب عليا"

إذا قال المستخدم **أجب عليا**:

- تتم الإجابة والنقاش فقط.
- لا يعدل الكود.
- لا تنشأ ملفات تنفيذ.
- لا تنفذ Migration.
- لا تنشأ Patch تنفيذية.

الاستثناء الوحيد: إذا قال المستخدم أيضًا **ذكرني لاحقًا** فيتم تسجيل البند بالتوثيق حسب الاتفاق.

## 10. قاعدة "نفذ الآن"

التنفيذ البرمجي يبدأ فقط بأمر صريح من المستخدم مثل:

**نفذ الآن**

طلب تحديث التوثيق بحد ذاته يسمح بتعديل ملفات التوثيق فقط، ولا يعني السماح بتعديل الكود.

## 11. قاعدة قاعدة البيانات

أي تغيير قاعدة بيانات يتم هكذا:

1. يحدد التغيير المطلوب.
2. يرسل للمستخدم SQL خطوة واحدة فقط.
3. ينفذ المستخدم الأمر يدويًا.
4. يرسل المستخدم النتيجة.
5. تتم مراجعتها.
6. بعدها فقط ترسل الخطوة التالية.
7. عند نجاح التغيير يتم تحديث ملف Schema وتسليمه للمستخدم.

لا ينفذ المساعد أوامر قاعدة البيانات مباشرة.

## 12. قاعدة المخزون

PM V2 لا تخصم Stock مباشرة.

كل صرف/تحويل/استخدام مادة يمر عبر منطق المخزون الحالي بكل قواعده، ومنها:

- التحقق من الرصيد.
- QR/Barcode.
- Lot Tracking.
- lot tracking token عند اشتراطه.
- Inventory Transaction الحالية.

PM V2 تحفظ مرجع الحركة وعلاقتها بالمهمة فقط.

## 13. قاعدة Path B

- لا يبنى Workflow شراء جديد.
- لا تعدل صلاحيات Path B الحالية.
- دور Warehouse لا يحصل تلقائيًا على صلاحية إنشاء PO.
- PM V2 تنشئ/تربط Bridge Ticket/Item عند الحاجة.
- يجب الحفاظ على سلسلة التتبع حتى Purchase Order.

## 14. التوثيق والحزم

كل تعديل فعلي يجب أن يحدث التوثيق المناسب.

كل Patch تسلم كـZIP صغير:

- الملفات الجديدة/المعدلة فقط.
- نفس بنية مجلدات المشروع.
- التوثيق المحدث.
- Manifest واضح.

## 15. الوحدة القديمة

Legacy Cleanup ليس جزءًا من بناء PM V2.

يبدأ فقط بعد:

- تشغيل PM V2 فعليًا.
- نجاح UAT وRegression.
- اعتماد المستخدم.
- فترة استقرار كافية.
- فحص Dependencies منفصل.
