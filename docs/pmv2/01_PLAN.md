# خطة التنفيذ المعتمدة — PM V2

## 1. الفلسفة التنفيذية

PM V2 ستبنى كـ **Bounded Module مستقل معماريًا داخل البرنامج الحالي**.

لن نبني تطبيقًا منفصلًا ثم نحاول ربطه في النهاية، ولن نخلط منطق PM V2 مباشرة في الوحدات القائمة.

المنهج هو:

**نفهم الموجود ونثبت عقود الربط → نبني قلب PM V2 داخل حدود مستقلة → نربط كل خدمة حالية في مرحلتها المناسبة → نختبر البرنامج كله كوحدة واحدة.**

## 2. قاعدة ملكية البيانات والوظائف

### PM V2 تملك

- التخصصات التنظيمية.
- فرق الصيانة.
- ربط أعضاء الفرق بالمستخدمين الحاليين.
- مسؤول التخصص.
- Checklists.
- Recurrence.
- Maintenance Programs.
- Due Engine / Scheduler.
- Tasks / Task Items.
- Visits / Visit Members.
- Follow-up Repair.
- Material Request lifecycle من منظور الصيانة.
- Final Closure.
- PM V2 operational audit.

### PM V2 لا تملك ولا تكرر

- Sites.
- Sections.
- Assets.
- Users.
- Warehouses.
- Catalog Items.
- Inventory / Lots / Transactions.
- Purchase Workflow.
- Path B.
- Purchase Orders.

تستخدم هذه العناصر من البرنامج الحالي عبر Adapters.

# مراحل التنفيذ

## المرحلة 0 — Existing Capability Audit + Design & Integration Freeze

**الحالة:** قيد التنفيذ. Step 0.1 (Existing Capability Audit من الكود) مكتملة؛ Reality Check من DB وDesign Freeze النهائي ما زالا مفتوحين.

المرجع التفصيلي:

- `12_EXISTING_CAPABILITY_AUDIT.md`
- `13_PHASE0_DESIGN_FREEZE.md`

### الهدف

منع التكرار وإغلاق التصميم قبل أي كود.

### العمل

1. جرد كل قدرة موجودة في البرنامج يمكن أن تحتاجها PM V2.
2. تحديد Source of Truth لكل مفهوم:
   - الموقع.
   - قسم الموقع.
   - الأصل.
   - القسم الوظيفي.
   - المستخدم/الفني.
   - المخزن.
   - الصنف.
   - المخزون.
   - البلاغ.
   - Purchase Order.
3. مراجعة البيانات الفعلية، وليس Schema فقط، لـ:
   - `sites`
   - `sections`
   - `assets`
   - `users`
   - `warehouses`
4. تثبيت الهيكل:
   **القسم الحالي → التخصص → الفريق → الأعضاء**.
5. تثبيت State Machines لـ:
   - Task.
   - Task Item.
   - Visit.
   - Material Request.
6. تحديد من يملك كل Transition.
7. تثبيت قواعد الإغلاق والترحيل والمتابعة.
8. تثبيت Integration Contracts للـAdapters.
9. تحديد External IDs التي تخزنها PM V2.
10. تثبيت ERD النهائي بعد إزالة أي جداول مكررة للموجود.

### Acceptance Gate

لا تبدأ المرحلة 1 إلا إذا:

- لا يوجد مفهوم رئيسي له مصدر حقيقة مجهول.
- لا يوجد جدول PM V2 يكرر Master Data موجودة بلا مبرر.
- State Machines معتمدة.
- الصلاحيات والTransitions محددة.
- عقود الـAdapters محددة.
- الـERD النهائي قابل للتنفيذ.

## المرحلة 1 — PM V2 Foundation + Database + Security/Audit

### الهدف

إنشاء حدود الوحدة المستقلة داخل نفس البرنامج.

### العمل

- إنشاء جداول `pmv2_*` المعتمدة فقط.
- Namespace واضح للBackend.
- Namespace واضح للFrontend.
- Domain/Services/Repositories خاصة بالوحدة.
- Adapter interfaces.
- Authorization layer خاصة بـPM V2.
- Audit أساسي من البداية.
- Route/Menu registration بشكل Additive فقط.

### قاعدة DB

كل SQL يرسل للمستخدم خطوة بخطوة للتنفيذ اليدوي، ثم يتم تحديث Schema بعد نجاحه.

### Acceptance Gate

- الوحدة مسجلة بدون تغيير Workflow قائم.
- لا يوجد اعتماد عشوائي مباشر على وحدات النظام الحالي.
- Security/Audit الأساسي يعمل.
- Schema متطابق مع قاعدة البيانات بعد تنفيذ المستخدم للأوامر.

## المرحلة 2 — Organization Model: التخصصات والفرق والأعضاء

### الهدف

بناء الهيكل التنظيمي الخاص بالصيانة دون تكرار المستخدمين أو الأقسام الحالية.

### العمل

- Specialty.
- Specialty Manager.
- Team.
- Team Members من `users` الحاليين.
- Team Warehouse reference إلى `warehouses` الحالي.
- Team Device/User reference عند الحاجة.
- ربط/عرض القسم الحالي عند الحاجة دون نسخه.

### الهيكل

**القسم الحالي → التخصص → الفريق → الأعضاء**

مع الفصل بين:

- مسؤول التخصص.
- عضو الفريق.
- رئيس المهمة لكل زيارة.

### Acceptance Gate

- يمكن إنشاء تخصص وفريق وربط مستخدمين حاليين.
- لا يتم إنشاء Technician/User جديد.
- لا يتم إنشاء Warehouse جديد.
- لا يرى المستخدم نطاقًا غير مسموح به.

## المرحلة 3 — Maintenance Targets Integration

### الهدف

استخدام المواقع والأقسام المكانية والأصول الحالية كأهداف للصيانة بدل إنشاء مواقع PM V2 مكررة.

### العمل

إنشاء Maintenance Target Adapter يدعم، حسب التصميم النهائي:

- Site.
- Section.
- Asset.

وعرضها داخل PM V2 للبحث والاختيار والربط بالبرامج.

### قاعدة

لا تنشأ `pmv2_locations` أو `pmv2_location_groups` كـMaster Data موازية إلا إذا أثبت Phase 0 حاجة حقيقية واعتمدها المستخدم.

### Acceptance Gate

- الهدف المعروض في PM V2 هو نفس سجل البرنامج الحالي.
- تغيير اسم/حالة الموقع في المصدر يظهر في PM V2 حسب سياسة القراءة المعتمدة.
- لا توجد Duplicate Master Data.

## المرحلة 4 — Checklists + Recurrence

### الهدف

بناء قوالب فحص قابلة لإعادة الاستخدام مع جدولة لكل بند.

### العمل

- Checklists.
- Checklist Items.
- ترتيب البنود.
- تفعيل/تعطيل.
- Recurrence لكل بند:
  - daily
  - weekly
  - monthly
  - quarterly
  - biannual
  - annual
- Anchor date والضوابط المطلوبة.

### Acceptance Gate

- نفس Checklist يمكن ربطها بعدة أهداف دون نسخ.
- كل نوع تكرار يحسب الاستحقاق المتوقع.
- البنود المعطلة لا تدخل في الاستحقاق.

## المرحلة 5 — Maintenance Programs

### الهدف

إنشاء برنامج الصيانة من مكونات معتمدة.

### البرنامج يربط

### Acceptance Gate

- الفريق والChecklist صالحان وفعالان.

## المرحلة 6 — Due Engine + Scheduler + Task Generation

### الهدف

توليد المهام المستحقة بصورة آمنة وقابلة لإعادة التشغيل.

### القواعد

- يحسب الاستحقاق لكل Checklist Item.
- يجمع البنود المستحقة لنفس الفريق والهدف في مهمة واحدة.
- Snapshot للبنود المطلوبة وقت التوليد.
- Idempotent.
- لا Duplicate عند إعادة التشغيل.

### Acceptance Gate

- كل أنواع التكرار ناجحة.
- تشغيل Scheduler المتكرر لا يكرر المهمة.
- نفس الهدف لفريقين مختلفين ينتج مهام مستقلة صحيحة.
- التجميع داخل المهمة صحيح.

## المرحلة 7 — Technician Core Workflow

### الهدف

إثبات دورة PM V2 الأساسية قبل التكاملات الحساسة.

### التجربة

**مهامي اليوم → الهدف → ابدأ الزيارة → بند واحد → سليم/تم الإصلاح/يحتاج صيانة → التالي → إنهاء الزيارة**

### تشمل

- مهامي اليوم.
- بند واحد في الشاشة.
- سليم.
- تم الإصلاح بدون مادة.
- يحتاج صيانة كحالة تشغيلية، بدون ربط المخزون بعد.
- صورة/ملاحظة اختيارية.
- الرجوع للتصحيح.
- رئيس المهمة.
- المشاركون.
- فني من فريق آخر.
- Audit للأفعال.

### Acceptance Gate

- دورة برنامج → مهمة → زيارة → بنود → إنهاء زيارة تعمل من البداية للنهاية.
- تجربة الهاتف والآيباد مناسبة.
- لا يوجد اعتماد على Inventory أو Path B لإتمام السيناريو الأساسي.

## المرحلة 8 — Core Stabilization Gate

### الهدف

تثبيت قلب PM V2 قبل إدخال المخزون والمشتريات.

### العمل

- مراجعة Domain rules.
- مراجعة Authorization.
- مراجعة Audit.
- مراجعة Scheduler.
- اختبار Concurrency/duplicate scenarios المناسبة.
- إصلاح أي مشاكل متراكمة.

### Acceptance Gate

يجب أن يكون واضحًا أن أي مشكلة تظهر بعد هذه النقطة في المخزون/الشراء هي مشكلة Integration وليست خللًا غير محسوم في قلب PM V2.

## المرحلة 9 — Team Inventory Integration + QR/Lot

### الهدف

ربط استخدام مواد مخزن الفريق بنفس منطق المخزون الحالي.

### المسارات

- تم الإصلاح + استخدمت قطعة.
- يحتاج صيانة → سحب من مخزوني.

### القاعدة

PM V2 تجمع مدخلات الفني، لكن التنفيذ الفعلي يمر عبر Inventory/Warehouse Adapter إلى الآلية الحالية بكل:

- Stock validation.
- QR/Barcode.
- Lot Tracking.
- Tracking Token عند الحاجة.
- Inventory Transaction.

### Acceptance Gate

- نفس الحركة تعطي نفس أثر الحركة الحالية.
- لا يوجد خصم مباشر من PM V2.
- لا يوجد Double Deduction.
- المرجع للحركة محفوظ داخل PM V2.

---

## المرحلة 10 — Material Requests + Warehouse Flow

### الهدف

إدارة المادة غير المتاحة للفني وربطها بالمستودع.

### المسار

**يحتاج صيانة → طلب مواد → بانتظار المستودع**

المستودع:

- إذا متوفر: صرف/تحويل للفريق بالنظام الحالي.
- إذا غير متوفر: بدء الشراء الخارجي من PM V2 للانتقال للمرحلة التالية.

### قاعدة العودة

لا تصبح المهمة جاهزة للمتابعة لمجرد وصول المادة للمستودع.

المسار الصحيح:

**وصول → استلام → صرف للفريق → جاهزة للإصلاح**

### Acceptance Gate

- كل طلب مرتبط بالمهمة وبندها.
- الصرف/التحويل يستخدم Workflow الحالي.
- الحالة لا تتقدم قبل الحدث الصحيح.

---

## المرحلة 11 — Path B Bridge + Purchase Order Linking

### الهدف

ربط طلب المادة غير المتوفرة بمسار الشراء الحالي دون تغييره.

### السلسلة

`PM V2 Task → Task Item → Material Request → Bridge Ticket/Item → Purchase Order`

### القواعد

- PM V2 تنشئ/تربط Bridge المطلوب.
- Warehouse يبدأ الطلب من PM V2.
- المستخدم المخول أصلًا في Path B يكمل PO.
- لا تضاف صلاحية PO لدور Warehouse.
- الفني يرى حالات مبسطة فقط.

### Acceptance Gate

- PO مرتبط بالمهمة الأصلية وقابل للتتبع.
- Workflow وصلاحيات Path B لم تتغير.
- PO التقليدي خارج PM V2 ما زال يعمل كما كان.

---

## المرحلة 12 — Follow-up Repairs + Final Closure + Notifications

### الهدف

إكمال دورة الحياة بعد وجود عطل أو مادة معلقة.

### تشمل

- طلبات معلقة.
- حالات مبسطة للفني.
- زر تذكير.
- Ready Follow-up بعد الصرف للفريق.
- نفس Task تبقى مفتوحة لليوم التالي؛ لا تنشأ مهمة جديدة.
- Follow-up Visit مستقلة.
- رئيس وأعضاء زيارة المتابعة قد يختلفون.
- Final Closure rules.

### شرط الإغلاق

لا يغلق Task إذا:

- يوجد Task Item غير محلول.
- يوجد Material Request نشط.
- يوجد Follow-up مطلوب.
- توجد زيارة تنفيذ مطلوبة غير منتهية.

### Acceptance Gate

- الترحيل يعمل دون Duplicate.
- يستحيل الإغلاق المبكر.
- الإغلاق يحدث فقط بعد اكتمال كل الشروط.

### مسؤول التخصص يرى حسب صلاحياته

- مهام اليوم.

- الزيارات.

- لا يوجد تسرب بين تخصصات أو صلاحيات.
- الأرقام مشتقة من بيانات التشغيل الفعلية وليست نظامًا موازيًا.

### الاختبارات

- Users/permissions.
