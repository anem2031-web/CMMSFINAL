# إصلاح تحميل أصناف الاستلام للمستودع — 2026-09-08

## القرار المعتمد

تنفيذ مسار مخصص للاستلام يعتمد على أهلية بند طلب الشراء، مع إبقاء سياسات حالة الطلب والاعتمادات العامة كما هي. هذه حزمة الإصلاح المعتمدة بعد التحقيق في الطلبين PR-2026-0448 وPR-2026-0488؛ وهي مستقلة عن حزمة مطابقة مقاسات الخشب السابقة.

## السبب المثبت

- الشاشة القديمة تستدعي purchaseOrders.getById، الذي يطبق صلاحية فتح تفاصيل الطلب بالكامل.
- عند اعتماد دفعة لاحقة، يمكن أن تعود حالة الطلب إلى approved رغم وصول أصناف سابقة للمستودع.
- صلاحية عرض الطلب العامة ترفض warehouse لهذه الحالة، بينما admin وowner يتجاوزانها.
- أُرفق من البيئة الفعلية رد FORBIDDEN ورسالة «ليس لديك صلاحية للاطلاع على هذا الطلب» من assertPOVisible للطلب الداخلي 3600147، وهو PR-2026-0448.
- أُعيدت التجربة على PR-2026-0488: تغيّر من partial_purchase إلى approved بعد اعتماد الدفعة الثانية، وأكد المستخدم تعطل الشاشة.
- الشاشة كانت لا تعرض خطأ الاستعلام، فتبقى التهيئة غير مكتملة ويظهر «جاري تحميل الأصناف…».

## ما تغير

1. إضافة warehouseReceiptsV2.purchaseReceiptContext تحت warehouseProcedure الفعلي: warehouse وadmin وowner فقط. لا تعديل لصلاحية فتح الطلب العام.
2. يعيد رقم الطلب ومعرفه والحقول التي يحتاجها الاستلام فقط. البنود يجب أن تنتمي للطلب، وتكون delivered_to_warehouse، وألا يكون لها سند مرتبط بحالة confirmed. يُطبّق نطاق رقم الفاتورة عند إرساله.
3. تحويل WarehouseReceiveV2 إلى الاستعلام الجديد. عرض خطأ الاستعلام وزر إعادة محاولة، وحالة مستقلة لعدم وجود أصناف، وتهيئة نموذج جديد عند تغير الطلب أو الفاتورة.
4. داخل معاملة receiveFromPurchaseV2، وقبل إنشاء السند أو تحديث المخزون: قفل صفوف البنود المطلوبة وإعادة قراءة أهليتها والسندات المؤكدة باستخدام قراءة قفل حديثة. يمنع ذلك تكرار بند سبق إكمال إدخاله عبر هذا المسار، حتى لو بقيت الشاشة القديمة مفتوحة.
5. رفض تكرار نفس معرف بند الطلب في السند، ورفض السند الفارغ أو السند الذي لا يحتوي أي بند مرتبط بالطلب. الأصناف الإضافية غير المرتبطة تبقى مسموحة إلى جانب بند طلب صالح؛ الفاتورة التي لا ترتبط بأي بند طلب تستخدم مسار الاستلام المستقل.

## نطاق الأثر

- حالة الطلب قد تظل approved بعد اعتماد الدفعة الجديدة؛ هذا متوقع في الحل الأقل تأثيرًا الذي اختاره المستخدم.
- لا تعديل لمنطق إرسال واعتماد دفعات التسعير أو حزم الشراء أو تقارير الحالات أو الحارس العام.
- يبقى منطق تحديث الطلب إلى received بعد وصول جميع بنوده، الموجود سابقًا في حفظ الاستلام، كما هو.
- لا SQL أو migration، ولا تعديل يدوي للحالات، ولا حذف أو إعادة معالجة سندات سابقة.
- لم تتغير شاشة الاستلام المستقل أو اعتماد مسودات الفواتير.
- منع التكرار هنا حسب البند الذي لديه سند confirmed، وهي نفس قاعدة الأهلية المستخدمة أصلًا في قائمة إدخال المخزون. لا تستحدث الحزمة نظام استلام جزئي متعدد السندات للبند الواحد.

النتيجة: 17 اختبارًا ناجحًا، صفر فشل.

تشمل الاختبارات: الحارس الحقيقي لإجراء tRPC للأدوار المستودع والأدمن والمالك، رفض الأدوار الأخرى والمستخدم غير المسجل، أهلية 448 رغم رفض تفاصيل الطلب العام، استبعاد بند 258 المؤكد، ثبات أهلية بند 488 عند تغيّر حالة الأب، نطاق الفاتورة، الطلب غير الموجود وتعذر الاتصال، رفض البنود غير المورّدة أو التابعة لطلب آخر أو المكررة، فحص السند المؤكد أثناء الحفظ، وترتيب القفل والتحقق قبل الكتابة.

حدود الاختبارات: استُخدم الكود الفعلي للصلاحيات والأهلية مع بدائل اختبار لاتصال قاعدة البيانات. فُحصت شروط استعلامات Drizzle وطلبات القفل؛ لم تُنفّذ تجربة تزامن على MySQL الفعلي، ولم تُحفظ حركة مخزون في قاعدة المستخدم. فحص ربط الشاشة وحالاتها اختبار عقد مصدر، وليس تجربة متصفح فعلية بحساب المستخدم.

npm run build: اكتمل بناء الواجهة والسيرفر، مع التحذيرات السابقة خارج نطاق الإصلاح.
npm run check: لا يزال يفشل بنفس 507 تشخيصات النسخة السابقة؛ بعد توحيد أرقام الأسطر لم تظهر تشخيصات إضافية. لا يُدّعى اجتياز فحص TypeScript الشامل.
