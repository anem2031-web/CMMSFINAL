# الصرف التشغيلي الجماعي — 2026-10-28

الحالة: الكود والاختبارات المحلية مكتملة؛ تنفيذ SQL اليدوي والتجربة الحية على `copycmms2` لم يُنفّذا في هذه المهمة. لا اتصال بقاعدة بيانات، ولا صرف بيانات كشف الإكسل، ولا نشر على الإنتاج.

## السلوك

- يسمح للمستودع بإنشاء طلب من المخزون فقط. أصحاب صلاحية الإنشاء السابقون يستخدمون المخزون، والمالك ومدير النظام يستطيعان أيضًا الاختيار من الكتالوج. يوجد تحقق خادم مستقل للمصدر؛ مسار الإنشاء القديم من الكتالوج لا يقبل بقية الأدوار.
- اختيار مستودع واحد، وإضافة 1–20 صنفًا مختلفًا. لكل بند كمية صحيحة، وحدة مخزون ثابتة، موقع وقسم وفني. يظهر رصيد المستودع المحدد ومعاينة توزيع الكمية على أقدم اللوتات. يبقى سبب الصرف العام مطلوبًا كما في المسار السابق.
- زر «حفظ وإرسال» ينشئ أمرًا pending؛ لا حجز ولا خصم عند الإنشاء. يبقى اعتماد المستودع الحالي قبل الصرف.
- تظهر بيانات البنود للمستودع للقراءة فقط. ملاحظة الصرف والمستلم الفعلي اختياريان لكل بند؛ عدم اختيار مستلم فعلي يستخدم الفني المحدد. سند التسليم يحمل المستلم الفعلي، ويحتفظ بالفني المحدد في حقول الإسناد والملاحظات.
- زر واحد يصرف جميع البنود بمعاملة واحدة. يعاد فحص الهوية والدور والحالة والمستلمين والأرصدة، وتُقفل أرصدة المخزون ثم تُختار اللوتات بالأقدم. فشل أي بند أو سند أو سجل يعيد كل الخصومات. مفتاح العملية وبصمة المدخلات وقفل الأمر يمنعون التكرار والتأكيد المتزامن.
- يستخدم التنفيذ `issueDelivery` الحالي، مع تكاليف اللوت وسند لكل جزء مصروف منه. لا تغيير لتقييم المخزون أو متوسط التكلفة. الموقع والقسم ثابتان من بند الطلب، ولا يتغيران بتغيير المستلم الفعلي.
- بنود الكتالوج بلا رصيد تحتفظ بإضافة الاحتياج إلى مسودة الشراء الحالية مع موقع وقسم البند. لا تُصرف بقية البنود جزئيًا أثناء انتظار الشراء.
- الطلبات القديمة التي لا تحتوي `dispatchContext` تستمر بمسارها السابق. المسارات الجديدة لا تقبل صرف بند منفرد من طلب جديد.

## تجهيز القاعدة يدويًا

الملف: `01_copycmms2_manual.sql`. افحص اسم القاعدة ووجود العمود والجدول أولًا. نفّذ كل عبارة على حدة؛ لا تعِد إضافة عنصر موجود.

الإضافتان فقط:
1. عمود JSON اختياري `operational_issue_items.dispatchContext` لحفظ سياق كل بند ومصدر الاختيار. لا تعديل للبيانات القديمة.
2. جدول `operational_issue_batches` لحفظ المستلمين والملاحظات وبصمة الطلب ونتائج الصرف الذري، مع فهرس فريد للأمر وآخر لمفتاح العملية.

لا يوجد backfill أو تحديث لأرصدة/لوتات. لا تشغّل `db:push`. هذا الملف يستهدف `copycmms2` صراحةً ولا ينفذ شيئًا على `cmms`. يلزم بقاء مفاتيح التشغيل القائمة الخاصة بالصرف التشغيلي واللوتات والتكاليف مفعلة عند التجربة.

## القبول الحي المتبقي

بعد SQL وتشغيل النسخة على اتصال `copycmms2` المؤكد: إنشاء طلب ببندين من حساب المستودع، اختيار أقسام وفنيين مختلفين، الاعتماد، اختيار مستلم فعلي لأحد البنود وترك الآخر فارغًا، ثم تأكيد واحد. راجع سندات التسليم والأسماء والملاحظات وتكلفة كل لوت ورصيد المستودع. أعد الضغط/الإرسال للتحقق من عدم تكرار الصرف. جرّب رصيدًا ناقصًا وبند كتالوج بلا مخزون بحساب admin ثم دورة الشراء والاستلام والصرف. لا تُجرَ هذه التجارب على الإنتاج أو بيانات كشف الإكسل.

قيد قائم حافظ عليه التطوير: كميات سندات التسليم أعداد صحيحة. إذا استلزم FIFO جزءًا كسريًا من لوت، يُرفض الصرف برسالة مراجعة بدل التقريب أو تعديل مخطط المستندات المشتركة. كذلك لا يسمح النظام بتكرار نفس صنف الكتالوج داخل الأمر الواحد، اتساقًا مع قيده الفريد الحالي.
