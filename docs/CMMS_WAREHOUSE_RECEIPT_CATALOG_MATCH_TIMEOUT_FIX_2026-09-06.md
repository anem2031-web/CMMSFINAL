# إصلاح مطابقة أصناف استلام المخزون — PR-2026-0258

تاريخ الفحص: 2026-09-06. المصدر: ملفات 545.zip المرفقة في هذه المحادثة.

## النتيجة وحدود الإثبات

تم إثبات عيب برمجي في مقارنة المقاسات، وإعادة إنتاج غياب مهلة انتهاء طلب DeepSeek من الكود الأصلي، ثم إصلاحهما واختبارهما محليًا. لا تتضمن الملفات سجلات محاولتي الأدمن والمستودع أو نسخة بيانات تشغيل تسمح بإثبات سبب اختلاف المحاولتين تحديدًا. هذه ليست شهادة نجاح الاستلام في الإنتاج.

كان هذا التقرير موجودًا في الأرشيف ويصف إصلاحًا سابقًا، لكن ملفي التنفيذ في الأرشيف لم يحتويَا ذلك الإصلاح. وكان اختبار llmTimeout.test.ts موجودًا بالفعل رغم غياب timeoutMs من التنفيذ. لذلك أُعيد الفحص والتنفيذ ولم يُعتمد التقرير القديم دليلًا على إصلاح مطبّق.

## الدليل من الكود

1. `client/src/pages/inventory/WarehouseReceiveV2.tsx`:
   - الإدخال اليدوي ينسخ `catalogItemId` من بند الطلب إلى `linkedItemId` إن وجد.
   - `handleReviewNext` يطلب المطابقة فقط للبنود غير المرتبطة.
   - ينتظر `matchInvoiceItems` قبل `setStep("items")`، ويظهر الزر حالة الانتظار طالما الطلب pending.
2. `server/routers/catalog/catalog.router.ts`، الإجراء `itemSuppliers.matchInvoiceItems`:
   - يستخدم `catalogReadProcedure`.
   - المطابقة بدرجة 92 فأعلى تتجاوز AI. الدرجات الضعيفة قد تنتظر `applyAiSemanticDiscovery`.
3. `server/routers/_shared/procedures.ts`:
   - `catalogReadProcedure` يسمح صراحةً بدور warehouse، وكذلك admin وowner.
   - لا يوجد تفرع حسب الدور داخل خوارزمية المطابقة. معطيات الطلب/المورد/الربط والتوقيت ونتائج الاتصال الفعلية غير متاحة للمحاولتين، فلا يمكن الجزم بسبب اختلافهما.
4. `server/_core/catalog-item-matching.ts` في الأصل:
   - كان يجمع الاسم العربي والإنجليزي واسم المورد البديل ضمن نص مقاسات واحد.
   - مقارنة عدد المقاسات تفسر الترجمة على أنها أبعاد إضافية.
5. فُحص أيضًا `dist/index.js` الأصلي المرفق: يحتوي دمج الأسماء نفسه ولا يحتوي `timeoutMs`؛ وجود التقرير القديم لا يعني أن نسخة التشغيل مصححة.
6. `server/_core/llm.ts` في الأصل:
   - طلب قائمة النماذج وطلب الإكمال وقراءة الرد بلا مهلة مخصصة أو AbortSignal.
   - أُعيد إنتاج طلب لا يحسم بعد المهلة المطلوبة؛ الاختبار القديم الموجود في الأرشيف نفسه يفشل بانتهاء مهلة Vitest البالغة 5 ثوانٍ.

## الإصلاح

- مقارنة الأوصاف المستقلة كلًا على حدة بدل جمع أبعادها: الاسم العربي، الإنجليزي، واسم المورد البديل. وجود تعارض في أي مقارنة يظل مانعًا، والأبعاد المتكررة داخل الوصف الواحد لا تُحذف. مثال `5cm x 5cm` مقابل `5cm` يظل تعارضًا.
- إضافة `timeoutMs` اختياري إلى `invokeLLM`، وتعيين 15000 مللي ثانية لاستدعاءات المطابقة فقط. المهلة تشمل اكتشاف النموذج وطلب الإكمال وإعادة اختيار النموذج وقراءة جسم الرد.
- استخدام إشارة إلغاء مستقلة لكل استدعاء محدد المهلة حتى لا يلغي مستخدم طلب مستخدم آخر، ولا ينتظر طلبًا مشتركًا قديمًا بلا مهلة.
- عند فشل AI، يرجع المسار الحالي إلى نتائج المطابقة المحلية. لا تتغير صلاحيات الاستلام أو شروط اختيار الصنف.
- هذه مهلة لكل استدعاء LLM وليست حدًا زمنيًا لكامل HTTP أو قاعدة البيانات أو فاتورة متعددة الأصناف.

## التحقق

- تشغيل مستقل لدوال TypeScript الفعلية عبر Node مع بدائل اختبار لاتصال الشبكة والكاش: **13 تحققًا ناجحًا**، يشمل اللغتين، الوصف ثنائي اللغة، ذاكرة المورد، التعارض الحقيقي، تجاوز AI، مهلة اكتشاف النموذج والإكمال وقراءة الرد وإعادة الاختيار، عزل الإلغاء، وإثبات بقاء طلب التنفيذ الأصلي معلقًا. لم يتصل الاختبار بـ DeepSeek أو قاعدة الإنتاج.
- أظهرت Vitest نجاح الاختبارات الستة الجديدة واختبارات المهلة الستة، ونجاح اختبارات تحسين الكاش الأربعة. اكتملت نتائج الحالات لكن بعض عمليات مشغّل Vitest لم تُغلق في بيئة الفحص؛ لذلك لا تُعد هذه نتيجة نجاح شامل للمشغّل أو المشروع.
- مجموعة المطابقة القديمة: 10 حالات ناجحة وحالة واحدة فاشلة لوصف «2 ملي». أُعيد تشغيلها على الأصل وتأكد نفس الفشل. لم يتغير محلل اختصار «ملي» في هذه الحزمة.
- تحقق صياغة TypeScript للملفات الأربعة البرمجية: ناجح.
- `npm run build`: اكتمل بناء واجهة التطبيق وتجميع السيرفر بنجاح، مع تحذيرات بناء موجودة في ملفات خارج نطاق الإصلاح.
- `npm run check`: يفشل في الأصل والمصحح بنفس **507 أخطاء**. قورنت قائمة التشخيصات بعد توحيد مسارات النسختين وأرقام الأسطر وكانت متطابقة. لا يُدّعى اجتياز الفحص الشامل.
- تثبيت اعتماديات الاختبار تطلب `npm ci --legacy-peer-deps --ignore-scripts` بسبب تعارض peer dependencies الموجود أصلًا؛ ملفات الحزم والأقفال لم تعدل.

لتشغيل الاختبارات المرفقة في بيئة المشروع:

```bash
npm test -- server/tests/catalogWarehouseReceiptRegression.test.ts server/tests/llmTimeout.test.ts
```

1. فك ZIP في جذر المشروع حيث `package.json`، مع استبدال الملفات بنفس المسارات، دون إضافة مجلد أب.
2. أعد بناء التطبيق ثم أعد تشغيل خدمة السيرفر وفق آلية النشر لديك؛ تعديل ملفات TypeScript وحده لا يحدّث `dist/index.js` المستخدم بواسطة `npm start`.
3. بحساب المستودع افتح PR-2026-0258، واختر الإدخال اليدوي، ثم نفس المورد والفاتورة، واضغط «التالي: مراجعة الأصناف».
4. تحقق من ظهور الاقتراح الصحيح، وأكمل اختيار الصنف والاستلام، ثم اختبر طلبًا كان يعمل سابقًا.
5. إذا استمر التعليق، يلزم طلب Network الخاص بـ `catalog.itemSuppliers.matchInvoiceItems` وحالته ومدته وردّه وسجل السيرفر الموافق، وبيانات بند الطلب/المورد للمحاولتين. إذا كان الزر يعرض تحميل بنود الطلب بدل المطابقة، يلزم أيضًا رد `purchaseOrders.getById`. احذف بيانات الدخول والكوكيز ومفاتيح الخدمات قبل المشاركة.

سبب فرق المحاولتين حسب الدور يظل غير مثبت حتى تتوفر هذه البيانات أو يعاد الاختبار في البيئة الفعلية. لم يُختلق له تفسير أو تُوسع صلاحيات المستودع.
